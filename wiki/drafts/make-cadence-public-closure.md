The pursuit opened in April 2026 as a someday commitment: open-source Cadence as a framework others can actually use. The founding constraint — "don't ship a framework, ship a tool that works, then extract the framework" — held throughout. Four projects executed in parallel across six weeks under a single organizing question: what does a maintainer need to run this thing bidirectionally with outside users? The answer took shape as two hidden verbs (`/cadence:report`, `/cadence:incoming`), a project-origin ledger with auto-close wiring, and a new story about how Cadence consumes external tools. All four projects shipped done. No brainstorms were opened under this pursuit — the scope was concrete from the start, specified from felt need rather than surfaced from divergence.

The two feedback verbs form the core artifact. `/cadence:report` gives adopters a privacy-first path to file issues without leaking Cadence state — nothing goes to GitHub unless the user explicitly opts in and confirms the content in full before posting. `/cadence:incoming` closes the other side: a maintainer-mode triage view that walks open issues one by one and routes each into Cadence-shaped state (action, project, capture, close, defer) so the inbound queue never lives only in GitHub. The origin field on projects and the auto-close path on resolve complete the loop — when a project promoted from an issue ships or gets dropped, the linked GitHub issue closes automatically with a comment naming the outcome. These three pieces together — report, incoming, origin-close — constitute the bidirectional OSS loop this pursuit was built around.

The MCP arc was the most architecturally eventful work. The first design built a standalone MCP client inside the cadence CLI, giving Cadence its own transport and configuration registry. That design failed on first real-server contact when the OAuth token for the HTTP MCP server turned out to live in macOS Keychain behind Claude Code's auth layer, inaccessible to a standalone process. The user's critique was direct: the cadence CLI is for local file-hierarchy mutations; MCP integration is network I/O with credentials. The pivot dropped the standalone client entirely — no TypeScript MCP client code, no `cadence mcp-pull` subcommand, no `@modelcontextprotocol/sdk` dependency — and reframed Cadence as a consumer of Claude Code's agent tool surface (`mcp__<server>__*`). That fixed the auth problem, but a second pivot followed when post-pivot testing showed the `cadence mcp-list` discovery layer and `cadence.yaml mcp_servers` registry were also dead weight: the agent's ToolSearch is already the registry. Deleting the parallel registry removed a class of misleading config paths that looked valid but couldn't reach the agent. What remained — the `/cadence:mcp-pull` skill, the `cadence write-capture --mcp-*` flags, and the capture `mcp:` frontmatter shape — is thinner and rests on the right abstraction. Work-computer validation also surfaced a latency finding worth preserving: the user-direction rule ("external tools require explicit direction, not agent initiative") is the right line to defend, but at Glean MCP's observed latency (10+ minutes per file read vs. instant in Glean's own chatbot), inline real-time lookups during verb flows are practically painful; the batch-ingestion path via `/cadence:mcp-pull` is the viable flow for corpus-heavy work.

What shifted through this pursuit: Cadence now has a maintainer-side surface that did not exist before. The user→issue→triage→action loop is closed without leaving the system. The MCP integration shape is now skill-driven rather than client-driven — a structural decision that respects Claude Code's authority over transport and auth rather than duplicating it. The tool-discipline rule in the runtime ("agent initiative" vs. "user direction") came directly from validation findings and now applies broadly across MCP, web search, and any other ambient tool surface. The no-brainstorms signal is also real data: this pursuit moved fast because the need was concrete. Execution-heavy pursuits don't always need a divergence phase — when the problem is clear, the right move is to start working it.

With `make-cadence-public` archived, the active surface is one pursuit lighter. Whatever is next on the open surface — `improve-ux-and-vision` work, structural changes, the next concrete bet — picks up from a Cadence that now has a working OSS feedback loop running under it.
