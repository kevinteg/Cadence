# The AI-Assisted Research-to-Writing Pipeline: A Practitioner's Survey for a Claude-Code-Centric, Markdown-First Workflow

> The deep-focus finding of this survey — the LLM-wiki pattern and its Cadence mapping — is distilled in [[llm-wiki-pattern]].

## TL;DR
- **Your existing workflow — wide-net research → per-source summaries → consolidation/clustering → cross-cluster synthesis → scaffold → first draft — is a recognized, validated pattern.** It is essentially hierarchical/map-reduce summarization plus Tiago Forte's "progressive summarization" and the Zettelkasten "assemble-from-notes" method. The single highest-leverage upgrade is to stop treating it as an in-chat process and persist every layer as Markdown in a Git repo, with Claude Code as the agent that ingests, summarizes, cross-links, and retrieves across it — the pattern Andrej Karpathy named the "LLM wiki."
- **For the living-docs/discovery layer, the strongest fit for your stated preferences is a three-layer Markdown repo (immutable `raw/` → LLM-maintained `wiki/` → a `CLAUDE.md` schema) with an `index.md` catalog and append-only `log.md`.** For a personal corpus under roughly 150–200 dense pages this beats vector RAG on reliability and simplicity; add local semantic search (Smart Connections, or the `qmd` hybrid-search engine Karpathy recommends) only when the agent starts missing things it should find.
- **Adopt SaaS tools surgically, not as the backbone:** NotebookLM is the best source-grounded "interrogate these 50 PDFs" surface; Obsidian is the best human-facing reader/graph over the same Markdown files; Notion AI/Mem/Tana/Reflect are heavier, lock-in-prone alternatives worth knowing but secondary to a file-based, Git-persisted core. The framework-assembly approach **does** extend to long-form works — named authors use AI to build a chapter scaffold first, then assemble sections from notes rather than free-writing.

## Key Findings

1. **Your method has names and a literature.** The per-source→consolidate→synthesize loop is *map-reduce / hierarchical summarization*; the layered distillation is Forte's *Progressive Summarization*; the "keep lots of context to backfill" instinct is the Zettelkasten/Second-Brain principle of preserving provenance and intermediate packets. You are not doing something idiosyncratic — you can borrow mature tooling and vocabulary.

2. **Claude Code is a legitimate writing-and-research engine, not just a coding tool.** Its primitives map cleanly onto your pipeline: **subagents** for parallel wide-net research (each in its own context window, returning only summaries), **slash commands/skills** for repeatable stages (`/headlines`, `/seo`, `/outline`, `/draft`), **CLAUDE.md** as the persistent index/schema/style guide, **hooks** for deterministic automation (auto-format, auto-commit, provenance stamping), and **MCP servers** to reach external sources.

3. **The "LLM wiki" pattern (Karpathy, April 2, 2026) is the definitive articulation of your discovery layer.** Immutable raw sources, an LLM-maintained interlinked Markdown wiki, and a schema file — with the explicit insight that for personal-scale corpora, a well-structured Markdown repo plus an `index.md` *outperforms* RAG on retrieval reliability and infrastructure cost. Within five days of posting, the original tweet had 16M+ views and the GitHub gist 5,000+ stars.

4. **Retrieval ergonomics: structure beats embeddings until you scale.** Frontmatter/YAML metadata + Dataview/Bases queries + Maps of Content + an index file get you most of the way. Semantic search (local embeddings via Smart Connections, `qmd`, or a LlamaIndex/ChromaDB setup) is a later add-on for large vaults, not a starting requirement.

5. **Framework assembly extends to long-form.** Named practitioners (Kenny Kane, Anna Bergevin), the Holiday/Greene notecard system, and Ahrens' Zettelkasten all describe building an outline/scaffold first and assembling sections from notes — confirming your "assemble a framework rather than free-write" hypothesis applies to books and long reports.

6. **Provenance is a solved problem in Markdown PKM.** Obsidian Web Clipper stamps `source`, `author`, `published`, `url`, and capture date into YAML frontmatter; Zotero + plugins (ZotLit, Zotero Integration, Citations) link literature notes back to raw sources via citekeys and Zotero URIs.

## Details

### Part A — The End-to-End Pipeline: Named Patterns and Concrete How-To

**A1. Map-reduce / hierarchical summarization (your consolidation step, formalized).**
The classic pattern from distributed computing has been adapted directly to LLM document work: *map* (summarize each source/chunk independently), then *reduce* (combine intermediate summaries, recursively re-summarizing if they exceed context). This is exactly your "summaries per initiative → consolidate like areas → synthesize across." Practitioners note hierarchical summarization "can match or slightly outperform full-context processing at substantially lower cost," and recommend ~10% chunk overlap to preserve context at boundaries. The variations worth knowing:
- **Stuff** (concatenate everything into one prompt) — only for small source sets that fit in context.
- **Map-reduce** — your default for many sources; parallelizable and debuggable.
- **Refine** (iteratively update a running summary source-by-source) — better coherence, less parallelism.
A research arc you can borrow: a "similarity-ordered" reduce step, where intermediate summaries are clustered by embedding similarity before merging, so related material consolidates together — a more principled version of your "consolidate like areas."

**A2. Progressive Summarization (Tiago Forte).** Forte's four layers — (1) captured passage, (2) bolded key sentences, (3) highlighted best of the bold, (4) a one-to-two-sentence executive summary in your own words — are a manual analogue of your layered summarization. The companion concepts you should steal: **PARA** (organize by actionability: Projects/Areas/Resources/Archives) and **Intermediate Packets** (treat every summary, outline, and draft fragment as a reusable asset, never start from a blank page). Forte's rule "never highlight more than 10% of the source" is a useful discipline for AI summarization prompts too.

**A3. Zettelkasten / "How to Take Smart Notes" (Sönke Ahrens) — the assemble-from-notes engine.** Ahrens systematized Luhmann's method into three note types: **fleeting** (capture), **literature** (in your own words, with the source), and **permanent** (atomic, self-contained, written as if for publication). The published step sequence is explicitly assembly-first: "Work out your ideas from the bottom up using the slip box. Choose the topics you want to write about from the outline. Shrink your existing notes into a first draft. Edit and proofread." The signature reframing — "Writing is not what happens after thinking. Writing is the medium of thinking" — anchors the claim that a manuscript can be *assembled* rather than *written from scratch*. The supporting evidence is Luhmann's own output: starting in 1952–53 he built a Zettelkasten of some 90,000 index cards and credited it for enabling roughly 50–70 books and ~400–550 published articles (counts vary by source). **Structure Notes / Maps of Content** act as the table-of-contents scaffolding over clusters of permanent notes — the direct ancestor of your "scaffolding first" step.

**A4. Evergreen notes & digital gardens (Andy Matuschak, Maggie Appleton, Tom Critchlow).** Matuschak's *evergreen notes* are "written and organized to evolve, contribute, and accumulate over time, across projects" — atomic, concept-oriented, densely linked. This is the philosophy that turns your kept-context corpus into a compounding asset rather than disposable scratch. Appleton's "A Brief History & Ethos of the Digital Garden" (2020) defines six patterns (topology over timeline, continuous growth, imperfection/learning in public, etc.). Critchlow's "of gardens and wikis" and the underlying stock-vs-flow distinction (Robin Sloan) explain *why* to invest in durable "stock" notes over ephemeral "flow" — and Critchlow built his garden as plain files+folders in Jekyll on GitHub Pages, exactly your preferred substrate.

**A5. Simon Willison's practical stance.** Willison's widely-cited mental model: treat the LLM as "an over-confident pair programming assistant," lightning-fast at lookups but prone to confident mistakes — so manage its context deliberately and verify outputs. His "AI assisted search-based research actually works now" (April 21, 2025) marks the point where tools like o3 became trustworthy enough that, in his words, "I think I might trust them enough that I'll skip my own fact-checking for lower-stakes tasks. I still don't trust them not to make mistakes" — *with the crucial caveat that he values transparency*: "The user-facing Google Gemini app can search too, but it doesn't show me what it's searching for. As a result, I just don't trust it... o3 is much more transparent." His `llm` CLI (with `-f`/fragments to load whole repos, files, or GitHub issues into context) is a Unix-philosophy, Markdown-friendly companion that fits your local-first bias and complements Claude Code.

**A6. The "interview me first" drafting pattern.** A recurring high-value technique across sources: before drafting, have the model interview *you* to build the spec/outline. Anthropic's own Claude Code guidance recommends: *"Interview me in detail using the AskUserQuestion tool. Ask about technical implementation, edge cases, and tradeoffs... then write a complete spec to SPEC.md. Once the spec is complete, start a fresh session to execute it."* Anna Bergevin uses the identical trick for book chapters — training Claude to "be an amazing interviewer, continually prompting me until we both felt like we had enough context," then having it turn the conversation into a detailed chapter outline. This is your "scaffolding first" step, supercharged.

### Part B (GO DEEP) — The Living-Docs / Discovery / Retrieval Layer

**B1. The LLM Wiki pattern (Andrej Karpathy, gist posted April 2, 2026) — your blueprint.** This is the single most important source for your deep-focus area. The architecture has three layers:
- **Raw sources** — "immutable — the LLM reads from them but never modifies them. This is your source of truth."
- **The wiki** — "a directory of LLM-generated markdown files. Summaries, entity pages, concept pages, comparisons, an overview, a synthesis. The LLM owns this layer entirely."
- **The schema** — "a document (e.g. CLAUDE.md for Claude Code...) that tells the LLM how the wiki is structured, what the conventions are, and what workflows to follow." Karpathy: "This is the key configuration file — it's what makes the LLM a disciplined wiki maintainer rather than a generic chatbot."

The three operations are **Ingest** (drop a source in raw/, LLM reads it, discusses takeaways, writes a summary page, updates the index, updates relevant entity/concept pages, appends to the log — "a single source might touch 10-15 wiki pages"), **Query** (LLM reads the index first, drills into relevant pages, synthesizes with citations — and crucially "good answers can be filed back into the wiki as new pages" so explorations compound), and **Lint** (periodic health-check for contradictions, stale claims, orphan pages, missing cross-references, gaps). Karpathy's framing: *"Obsidian is the IDE; the LLM is the programmer; the wiki is the codebase."*

Two navigation files do the heavy lifting:
- **`index.md`** — content-oriented catalog: every page with a link, one-line summary, optional metadata. "When answering a query, the LLM reads the index first to find relevant pages, then drills into them. This works surprisingly well at moderate scale (~100 sources, ~hundreds of pages) and avoids the need for embedding-based RAG infrastructure." (Karpathy's own wiki reportedly reached roughly 100 articles and ~400,000 words while the LLM still navigated it efficiently via the index and summaries — and, by his account, faster and more accurately than a RAG pipeline.)
- **`log.md`** — append-only chronological record. Tip: consistent prefixes like `## [2026-04-02] ingest | Article Title` make it greppable (`grep "^## \[" log.md | tail -5`).

Karpathy explicitly contrasts this with RAG: in RAG "the LLM is rediscovering knowledge from scratch on every question. There's no accumulation." The wiki, by contrast, is "a persistent, compounding artifact" — cross-references already there, contradictions already flagged. **Why it works:** "The tedious part of maintaining a knowledge base is not the reading or the thinking — it's the bookkeeping... Humans abandon wikis because the maintenance burden grows faster than the value. LLMs don't get bored." The pattern is consciously a realization of Vannevar Bush's 1945 Memex; "the part he couldn't solve was who does the maintenance. The LLM handles that."

**B2. The context-vs-RAG threshold (the practical decision rule).** A widely-corroborated rule of thumb emerged in the LLM-wiki discussion: below ~50k–100k tokens (~150–200 dense pages), keep everything in context / use the Markdown-wiki approach — you get "100% retrieval reliability (no missed chunks, no semantics broken by chunking), near-zero infra... and global reasoning over the whole corpus." Millions of tokens: RAG becomes necessary. In between / production: hybrid (stable core in context, dynamic/massive records behind RAG). For your use case — background research per initiative — most individual projects sit well below the line, so **prefer structured Markdown + index over a vector DB.** An `index.md` "isn't RAG — it does no vector matching and no chunking; it just lets the agent open fewer whole files as the library grows."

**B3. Claude Code as the retrieval/discovery interface — concrete setups.**
- **Stefan Imhoff's "Agentic Note-Taking"** is a fully worked example: he ran Claude Code's `/init` on his Obsidian vault to auto-generate a `CLAUDE.md` describing folder structure (Zettelkasten `YYYYMMDDHHmm.md` filenames, PARA folders, Daily, Meta), then "taught Claude Code to use the qmd and obsidian commands to manage my vault," where `qmd` is "significantly faster than the built-in Obsidian search." His verdict: "Markdown is the perfect format for LLMs to consume, and Obsidian is the perfect tool for creating and managing markdown notes."
- **`qmd`** (repo `tobi/qmd`, by Shopify co-founder/CEO **Tobi Lütke**, public December 8, 2025; 22,000+ GitHub stars by April 2026) is "an on-device search engine for everything you need to remember." It combines BM25 full-text search, vector semantic search, and LLM re-ranking, and ships as both a CLI and an **MCP server** so Claude Code and other agents can query a personal corpus natively. Karpathy specifically recommends it as the search tool to add once the index file alone isn't enough; it's also packaged as a **Claude Code Skill**.
- **"Ask my notes" semantic tasks**: practitioners report Claude Code reading and *understanding* note contents to find redundant/orphan notes, generating MOC-style summary notes that link back via Obsidian `[[wikilinks]]`, and producing flashcards — i.e., the agent acts as a librarian over the corpus, not just a search box.
- **Claude Cowork** (the agentic, folder-oriented surface) sits "between NotebookLM and Claude Code" — it reads/edits Obsidian vaults with zero friction because they're just Markdown folders; documented users built skills that ingest "phone dumps" into a tagged vault in seconds, and had Claude design a hybrid Zettelkasten/PARA/MOC navigation system for an existing vault.

**B4. Structuring for discoverability — frontmatter, MOCs, queries.**
- **YAML frontmatter / Properties** are the queryable metadata layer. Obsidian's newer **Bases** reads *only* frontmatter (not inline `field:: value` Dataview syntax), so for forward-compatibility put anything you'll sort/filter on into formal YAML properties. Use ISO dates (`YYYY-MM-DD`) for sortable capture dates, `url` type for source links, and list-type `tags`/`authors`.
- **Maps of Content (MOCs)** (Nick Milo's LYT method) are manually-curated index notes. They can be automated into **"Dynamic MOCs"** via an embedded Base or Dataview query (e.g., "all notes tagged #project-management"), turning a static list into a self-updating discovery engine.
- **Tags vs links:** a link (`[[Note]]`) is a direct, explicit connection forming the network's core; a tag (`#topic`) is a broad categorical filter. Atomic notes + contextual linking (Zettelkasten) generally beat deep folder hierarchies for serendipitous retrieval.
- **Dataview / Bases** turn frontmatter into live tables — e.g., a daily-note query listing today's clips where `status: inbox`, processed in five minutes a day.

**B5. Semantic search / local RAG over notes — the optional upgrade.**
- **Smart Connections** (Brian Petro) — zero-setup, local on-device embeddings; "Connections" sidebar surfaces semantically related notes as you write, "Lookup" gives a private semantic search engine; free Core tier, no API key, works offline after indexing. Storage ~3 MB per 1,000 notes. Most-recommended starting point.
- **Copilot for Obsidian** — conversational vault-wide Q&A (RAG over your vault); can run fully local via Ollama (`nomic-embed-text` for embeddings, an 8B model like llama3.2 for chat).
- **VaultSearch / Similar Notes / obsidian-qmd** — local hybrid (BM25 + vector) search plugins, on-device, no cloud.
- **Roll-your-own**: LlamaIndex or LangChain over a vault (one practitioner embedded ~2,000 notes with OpenAI embeddings in 40 seconds for 8 cents, storing `[[wikilink]]` relationships to enable GraphRAG); ChromaDB + SentenceTransformers (`all-mpnet-base-v2`) for a local-first weekend build; `txtai` for an embeddings database. **ObsidianRAG** and **obsidian-local-llm-hub** are turnkey local options (hybrid search + reranking + GraphRAG following `[[wikilinks]]`, all offline via Ollama/LM Studio).
- **Key quality insight:** "Well-structured notes with clear headings and explicit conclusions produce much better RAG answers than stream-of-consciousness writing." Improving note structure often helps retrieval more than changing the model — which reinforces the value of your summarization-and-consolidation discipline.

**B6. Provenance and citation (so you can backfill).**
- **Obsidian Web Clipper** (official, free) converts web pages to Markdown and writes frontmatter properties: `{{title}}`, `{{author}}`, `{{published}}`, `{{url}}`, `{{date}}`, with per-site/schema.org templates. A practical minimal block to stamp on every clip: `source:`, `author:`, `clipped:` (ISO date), `tags:`, `status: unread`. Rationale: "A clipped article is only valuable if you can find it again. Frontmatter is how you make that work — it's what powers Dataview queries." Gotcha: a Templater template on the clippings folder can overwrite Web Clipper's frontmatter — separate the two (Clipper sets frontmatter, Templater runs afterward).
- **An `inbox` status pattern**: every clip gets `status: inbox`; a daily-note Dataview query lists the day's clips filtered on that field, and you triage into literature notes in ~5 minutes.
- **Zotero + Obsidian** for heavier citation needs: **ZotLit** (reads Zotero's DB directly, fast; pulls metadata, annotations, image highlights; drag-and-drop annotations include a URI backlink to the source PDF in Zotero), **Zotero Integration** (mgmeyers; `Create Literature Note` command, one note per source, citekey-titled), and the **Citations / Simple Citations** plugins (auto-append title, authors, journal, year, DOI, and Zotero URI to frontmatter). Academic practitioners (e.g., Alexandra Phelan) title literature notes `@citekey` so "the difference between a citation and an internal link to the Literature Note is simply a matter of square brackets," with BetterBibTeX generating keys like `auth + "-" + year`.
- **Provenance in the LLM-wiki context**: community implementations add source metadata, timestamps, and hashes per ingest so unchanged files are skipped and "a poisoned entry is findable and revertible" — and the whole wiki being a Git repo gives you version history, diffs, and the ability to trace any claim back to its commit.

### Part C — Tool-by-Tool Fit Assessment (against your Claude-Code-centric, Markdown, GitHub, local-first preferences)

**Best fit (file-based, Markdown, local, Git-friendly):**
- **Claude Code** — the orchestration core. CLAUDE.md as schema/index/style guide; subagents for parallel research; skills/slash commands for pipeline stages; hooks for deterministic automation; MCP for external sources. Native fit.
- **Obsidian** — the human-facing reader/editor/graph over your Markdown. Plain `.md` files = zero lock-in; graph view shows wiki shape; Bases/Dataview for structured queries; vast plugin ecosystem (Smart Connections, Copilot, qmd). Karpathy's recommended front-end. Excellent fit.
- **`qmd`** — local hybrid search as CLI + Skill + MCP. Purpose-built for this. Excellent fit.
- **Simon Willison's `llm` CLI** — Unix-pipe LLM access, fragments to load files/repos/issues, local-model support via Ollama. Strong fit, complements Claude Code.
- **Git/GitHub** — version control of raw sources, wiki, drafts; diffs, history, branching for free. Your stated persistence layer; native fit.
- **Logseq** — local-first Markdown(ish) outliner with backlinks; good if you think in outlines. Note: still effectively beta (latest 0.10.15, Dec 2025); data is block-based, slightly less portable than flat Markdown. Good fit with caveats.

**Useful but heavier / partial fit:**
- **NotebookLM** (Google) — best-in-class *source-grounded* Q&A over up to 50 uploaded sources per notebook, with clickable citations to exact passages; generates briefing docs, FAQs, timelines, audio overviews. SaaS, cloud-only, notebooks share only within org; not Markdown-file-based. Use it as a **bounded interrogation surface** for a defined source set, then export findings to your repo. Strong complement, weak as backbone.
- **Cursor** — IDE-first AI editor; excellent inline-edit UX, but optimized for code-in-IDE rather than agentic file-corpus research. Fine if you already live in it.
- **Notion AI** — polished, collaborative, "Ask Notion" across workspace; but proprietary format, cloud, full AI needs Business plan (~$20/user/mo). Lock-in risk; weak fit for local-first/Markdown.
- **Tana** — powerful "supertags" (schema/typed objects) and queries; cloud-only, proprietary. Great for structured data modeling, against your local-first bias.
- **Reflect** — polished, E2E-encrypted, calendar-integrated, built-in GPT-4o/Claude; cloud, paid (~$10/mo). Pleasant but proprietary.
- **Mem** — strongest AI auto-organization (no manual filing); web-first, paid (~$12–15/mo), proprietary format. Against local-first/Markdown.
- **Roam Research** — pioneered networked thought/block references; subscription-only, proprietary. Largely superseded by Obsidian/Logseq for your preferences.

## Recommendations

**Stage 1 — Re-platform your existing workflow onto Git + Markdown + Claude Code (do this first).**
1. Create one Git repo per major initiative (or one repo with per-initiative folders) with three directories: `raw/` (immutable captured sources), `wiki/` (LLM-maintained summaries, concept/entity pages, syntheses), and a root `CLAUDE.md`.
2. Write `CLAUDE.md` as your schema + index + style guide: folder conventions, your summarization layers (per-source → consolidated → synthesis), naming conventions, and your *voice/style rules* (tone, banned phrases). Keep it under ~200 lines and use progressive disclosure — point to detail files rather than inlining everything.
3. Maintain `index.md` (catalog: each wiki page + one-line summary) and an append-only `log.md` with greppable `## [YYYY-MM-DD] ingest | Title` prefixes.
4. Run your existing loop *through Claude Code*: ingest sources into `raw/`, have Claude write per-source summaries, consolidate like areas into cluster pages, synthesize across clusters, then generate the scaffold and first draft — each step a file the agent reads and updates.

**Stage 2 — Operationalize the repeatable stages.**
5. Build slash commands/skills for your recurring stages: `/ingest` (summarize a raw source, update index + log + related pages), `/consolidate` (cluster like summaries), `/synthesize` (cross-cluster), `/scaffold` (outline from synthesis + goal-alignment check), `/draft`. Store them in `.claude/commands/` (project) or `~/.claude/skills/` (global). Use slash commands for steps you trigger explicitly, skills for richer auto-invoked workflows with supporting files/templates.
6. Use **subagents** for the wide-net phase: dispatch parallel research subagents (each with `Read, Grep, Glob, WebFetch, WebSearch`) so verbose search results stay out of your main context and return only structured briefs — directly solving the context-bloat problem your "keep lots of context" habit risks.
7. Add a few **hooks**: a PostToolUse/Stop hook to auto-format Markdown and auto-commit (so every change is versioned and backfillable), and a SessionStart hook to inject current-state context. Adopt a `/lint` skill (Karpathy's health-check) to flag contradictions, stale claims, orphans, and gaps.

**Stage 3 — Provenance and discovery.**
8. Standardize capture: install **Obsidian Web Clipper** with a template stamping `source`, `author`, `published`, `url`, `clipped` (ISO date), `tags`, `status: inbox`. For PDFs/papers, add **Zotero + ZotLit** with `@citekey`-titled literature notes that backlink to source PDFs.
9. Open the same repo in **Obsidian** as your reading/graph/query surface; add **Smart Connections** for local semantic "related notes" with zero setup.
10. Triage daily: a Dataview query over `status: inbox` clips, processed in ~5 minutes into literature notes.

**Stage 4 — Long-form / framework assembly (when you tackle bigger works).**
11. For a book/long report, follow the named-author pattern: (a) human-only concept doc; (b) AI-assisted *chapter-level outline* you heavily revise into "the skeleton"; (c) AI-interview yourself per section to generate detailed sub-outlines with your notes organized; (d) assemble each section from your permanent notes ("shrink notes into a first draft"); (e) voice calibration and human synthesis pass. Keep the manuscript, outline, and editorial notes together in the repo so the agent reasons over the whole. Kenny Kane's six-stage Claude book workflow and Anna Bergevin's chapter-outline process are concrete, replicable templates; the Holiday/Greene notecard system (where "the categories of notes often correspond to later chapter titles") is the analog proof that note categories *are* the scaffold.

**Benchmarks that should change your approach:**
- **Stay with structured-Markdown-over-context** while a project's corpus is under ~150–200 dense pages (~50k–100k tokens). **Add semantic search/RAG** (Smart Connections → qmd → LlamaIndex) only when (a) the agent demonstrably misses notes you *know* exist, or (b) a corpus crosses roughly that token threshold.
- **Add a vector DB only at the millions-of-tokens scale**; below it, RAG is "pure overhead and a reliability downgrade."
- **Escalate from slash commands to skills** when a workflow needs supporting files/templates or you want auto-invocation; use **CLAUDE.md** only for short, always-true conventions (it loads into *every* session, so bloat degrades performance).

## Caveats
- **Source-quality flags:** Several how-to sources are vendor blogs (MindStudio/Remy, Atlas, various "best AI tool" listicles) with marketing incentives; I relied on them only for widely-corroborated mechanics, not product claims. The "write a book with Claude" practitioner pages (e.g., Kenny Kane) give concrete, replicable process steps but their time-savings figures ("saves 60% of drafting time," "80–100 hours") are self-reported, not verified. Anna Bergevin (first-person Substack with her full prompt shown) and Ryan Holiday (own site, verbatim quotes) are the strongest named primary sources for long-form assembly.
- **Recency/version churn:** Claude Code's feature set is moving fast (subagents, skills, hooks, "agent teams," and a research-preview "Dynamic Workflows" orchestrating up to ~1,000 subagents per the May 28, 2026 announcement). Treat specific command names, limits, and the Dynamic Workflows capability as point-in-time and verify against current docs. Logseq remains effectively beta (0.10.15, Dec 2025) — be conservative for mission-critical use.
- **LLM reliability:** Across every credible source the consistent warning holds — AI is a research assistant, not a source of truth. It hallucinates confidently; verify facts, especially numbers, links, and code, against primary sources. Willison's own threshold (trusting AI search for *lower-stakes* tasks only, and distrusting *opaque* tools) is the right calibration.
- **Provenance/security of auto-ingesting wikis:** An autonomously-ingesting LLM wiki is an indirect-prompt-injection surface — a crafted source can plant instructions that persist. Mitigations discussed by practitioners include treating source text as untrusted at every model boundary, git-backed per-claim provenance so poisoned entries are revertible, and a human review gate before promoting AI-written content. Keep a human in the loop on what gets "crystallized."
- **Don't over-engineer.** The strongest meta-finding is that a plain Git repo of well-structured Markdown plus Claude Code and an index file goes much further than most people expect. Add embeddings, vector DBs, and multi-agent orchestration only when a concrete retrieval failure justifies the complexity.
