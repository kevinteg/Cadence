First-class Markdown rendering for Cadence artifacts (cadence read)

Cadence artifacts are all Markdown (narratives, project files, reflections, brainstorm notes). The terminal is the primary surface, but there's no built-in way to read a doc rendered — you either read raw source or stand up an ad-hoc tool yourself. For long-form docs, a rendered view reads meaningfully better than raw source.

Hard constraint: rendering must be fully local (privacy). `grip` (the obvious GitHub-fidelity tool) POSTs to GitHub's API → disqualified.

Tools evaluated: glow (terminal fallback), mdcat (terminal alt), bat (syntax only — not md), grip (rejected: remote), pandoc → local HTTP → open (chosen path).

Key finding — opening a local page in iTerm2's built-in browser requires an http://localhost hop, not file://. iTerm2 registers as a URL handler only for http/https/x-man-page. `open -b com.googlecode.iterm2 file://…` is mis-routed and tries to run the file as a terminal command. `open -b com.googlecode.iterm2 http://localhost:8787/foo.html` works.

Proposed: cadence read <entity-or-path> verb that resolves a Cadence entity OR a raw path, renders locally to styled HTML (bundled CSS, prefers-color-scheme), opens in the terminal browser when iTerm2 is detected (localhost serve + open -b), falls back to system browser or glow when headless. Never transmits to remote.

Open design questions: bundle a renderer vs shell out (footprint vs zero-config); terminal fallback glow vs mdcat; built-in verb vs documented recipe; server lifecycle (persistent vs serve-and-exit).
